# CustodIA v1.1 — addendum: mobile-first, real execution, derivatives

> Extends `2026-09-11-custodia-v1-spec.md`. Where the two conflict, this addendum wins.
> Deadlines are out of scope here; this is the complete target, staged in the master plan.

## A. Mobile-first is a hard requirement

The product is reached from WhatsApp and Telegram. Every user-facing screen after the chat
message is a **mobile web view** (a link the bot sends, or a Telegram Mini App). Desktop is a
secondary rendering of the same components, never the design target.

1. **Signing works on a phone.** All wallet interactions (sign-in, mandate, revoke, ENS claim)
   go through **WalletConnect** (RainbowKit or the WalletConnect AppKit) with deep links to
   MetaMask Mobile / Rainbow / Coinbase Wallet. `window.ethereum` is a desktop-only fallback,
   never a requirement. Acceptance: the full chat → sign → task flow completes on iOS Safari and
   inside Telegram's in-app browser with no desktop involved.
2. **Telegram Mini App is the primary surface.** The review page, holdings and task pages open
   as a Mini App (server-side `initData` validation). The bot itself only carries intent,
   summaries, status changes and links. WhatsApp uses the same backend and links out to the
   web view (no Mini App equivalent).
3. **Touch is the interaction model.** Charts scrub by touch with a readable tooltip; controls
   have ≥ 44 px hit targets; chip groups scroll sideways; nothing depends on hover.
4. **One column, chart first.** Below 900 px, the generated UX renders the evidence (chart,
   holdings) before controls; controls collapse behind a single toggle.
5. **Performance budget.** First contentful paint < 2 s on a mid-range Android over 4G for the
   review page; charts render with data already in the HTML (no client-only fetch for the
   first paint).

## B. Real execution on testnet

Spot execution becomes real and is the only non-simulated execution path in v1.1.

- Stages 4 and 5 of the master plan are mandatory: `TaskVault` (owner funds, agent may only
  call the allow-listed Uniswap V2 Sepolia adapter, output stays in the vault, on-chain
  version/expiry/nonce/caps), an isolated **execution signer**, an isolated **policy signer**
  whose short-lived approval the vault requires, and the worker's evidence → preview →
  approve → submit → confirm → reconcile loop.
- Acceptance: one authorized swap completes with no second signature; an out-of-policy swap is
  refused by the service *and* reverts on-chain; killing the worker between submit and confirm
  leads to reconciliation, never double submission.
- "Rebalance" is expressed as one or more spot swaps inside the same mandate.

## C. Derivatives and protection — venue-dependent stages

Ethereum Sepolia has no usable perpetuals or options venue. These stages therefore introduce a
second execution environment. **Decision required (recommendation below):**

| Option | Where | Pros | Cons |
|---|---|---|---|
| GMX v2 on **Arbitrum Sepolia** | EVM L2 testnet | On-chain, EVM tooling identical, vault pattern reusable | Second chain: vault deployment, bridging test funds, separate keys |
| Synthetix v3 on **Base Sepolia** | EVM L2 testnet | Same as above; Base tooling strong | Same; perps market availability on testnet varies |
| **Hyperliquid testnet** | API-based venue | Fast, liquid, rich API | Custodial-style API keys; not the vault model — authority would sit in an API key, contradicting the product thesis |

**Recommendation:** GMX v2 on Arbitrum Sepolia, with the *same* `TaskVault` contract deployed
there and a `GmxPerpAdapter` as the allow-listed target. Authority stays on-chain and scoped.
Hyperliquid is rejected on principle: an API key is exactly the unbounded authority the
product exists to prevent.

- **Futures (Stage 8):** leverage disabled by default and only enabled by an explicit mandate
  field with a hard cap (≤ 3× in v1.1); stop required; the mandate names the venue, market,
  max notional, max leverage and expiry; the vault enforces them. Acceptance: one bounded
  position opened and closed autonomously; a leverage increase beyond the mandate reverts.
- **Protection (Stage 9):** a real hedge means a real quote. Until an options venue exists on
  a supported testnet, protection stays a **labeled model estimate** with the deductible /
  duration / premium-budget controls and a payoff comparison. If a venue becomes available,
  the premium becomes a quoted price and the purchase is an execution path under the vault.

## D. Product rules confirmed by the 2026-09-12 end-to-end run

These are now requirements, not observations:

1. **Only authorizable proposals can become mandates.** An escalation (`needs_human`) or a
   comparison grants no authority; the mandate route refuses them (409) and the UI never offers
   a signature for them.
2. **One ENS identity per wallet.** A second claim is refused; task subnames live under the
   first identity.
3. **Envelopes come from the wallet, not the prompt.** "Buy $500" on a $250 wallet becomes an
   escalation with the real envelope stated. Demo wallets must be funded to match the demo.
4. **Unsupported requests are answered, never faked.** Mainnet, bridges and unbounded execution
   return an explanation with no controls.
5. **Every autonomous action is recorded** (simulated ones labeled `simulated`), and revocation
   blocks the next action immediately (service) and on-chain once confirmed.

## E. Acceptance for v1.1 as a whole

From a phone, inside Telegram: sign in with a mobile wallet → claim `me.custodia.eth` → ask for
a guard → read the generated evidence by touch → sign a mandate → fund the vault → the worker
executes one permitted Sepolia swap and sends a receipt → an over-limit action is refused in
the service and on-chain → revoke from Telegram → the next action is refused. Futures: the same
loop on Arbitrum Sepolia with a bounded position. Protection: labeled estimate unless quoted.
